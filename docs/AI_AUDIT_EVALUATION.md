# AI 审计增益对照实验方案（CLI v1）

## 目标与结论边界

回答一个问题：在同一批 Java 审计任务、同一模型和相同预算下，允许 AI 使用 JByteScanner CLI，是否比仅使用代码搜索与字节码工具，更快或更准确地找出**可核实的 source-to-sink 问题**？本实验评估 AI 的审计结果，不以扫描报告条数作为成绩。

先做 10～20 个任务的试点。Groovy 脚本注入可作首个任务，但最终任务集还应包含其他漏洞类型、无漏洞样本，以及工具已知未命中或只能返回 `unknown` 的样本。真实项目没有完整真值时，只能报告“已核实问题的发现情况”，不能声称计算了项目整体召回率。

本方案使用纯 CLI，不需要 MCP，也不要求修改 JByteScanner。当前 `query` 仅支持完整 Tai-e source/sink 方法签名过滤，`finding` 也要求 `--sink`；批量输出包含完整 finding，可能很大。这些检索成本是实验对象的一部分，不要预先替实验组找好签名。

## 角色与材料

- **准备 agent**：准备相同的部署包、反编译代码、任务清单和实验组扫描工作区；记录版本与准备耗时。它不参与审计和裁决。
- **审计 agent**：每个任务、每个组、每次重复均使用全新会话。只读取任务说明和该组允许的材料；提交结构化结论。它不看答案、其他运行记录或另一组输出。
- **裁决 agent / 人工审计者**：在两组结果全部封存后，盲化组别并依据同一部署版本核验证据。不能仅因 JByteScanner 报告存在就判为真阳性；无法确定的标为 `uncertain`，交人工复核。

两组均可访问同一份部署包、同一份反编译代码，并使用 `rg`、文件查看、`jar`/`javap` 等常规只读工具。实验组额外获得 JByteScanner 的 `query`/`diagnose` 和**该包预先生成的** `.jbytescanner` 工作区。对照组不得读取该工作区、SARIF、sidecar、诊断 JSON、JByteScanner 日志或另一组的会话。实验组可以通过 CLI 查结果、查 `--help`；为保证检索成本可比，不直接读取 sidecar/SARIF 绕过 CLI。两组均不得修改目标或规则、启动业务服务、联网搜索答案，或运行新的全量扫描。

## 准备步骤（在实际测试电脑执行一次）

1. 固定 JByteScanner commit、JAR SHA-256、JDK、目标部署包版本和反编译工具版本。为每个部署包保存文件清单及 SHA-256。两组使用同一份反编译结果，允许代理继续使用常规字节码工具查细节。
2. 在隔离的目标副本上配置 `scan_packages`，检查候选包日志和 API 数量。如果人工决定加入第二业务包，记录理由，并运行 `-m api` 重新生成 `api.txt` 后再扫描。不要让审计 agent 看到这一步的诊断或扫描结果。
3. 对实验组运行一次普通扫描，检查 `query <workspace> scan-status --json` 中 `worker.status=SUCCESS`。封存这一份扫描工作区作为只读母版。准备时间与扫描时间单独记录；`diagnose` 的后续运行时间计入对应审计 agent 的预算。
4. 每次运行都从相同部署包、反编译代码和封存的扫描母版创建独立视图；B 组获得私有的可写 `.jbytescanner` 副本，因为 `diagnose` 会写入其中。可使用文件系统快照或写时复制减少 4 GB 级部署包的复制成本。A 组视图不含 `.jbytescanner`、JByteScanner 日志及答案；两组业务 JAR 和反编译代码均只读。通过独立目录/权限或工具白名单隔离，不只靠提示词保密；运行结束后不要把 B 组新增的诊断结果写回母版。
5. 由独立人员准备任务清单与真值候选。公开任务文件只写漏洞类别和业务范围，例如“检查 Groovy 脚本注入”，不写完整 sink 签名、finding ID、具体入口或预期结果。任务清单同时包含有已核实问题和经充分检查未发现问题的样本；真值文件仅由裁决者保存。

示例命令（替换路径；按实际机器调整 Java 内存和扫描参数）：

```bash
java -jar "$JBS_JAR" "$DEPLOYMENT" -m api
java -jar "$JBS_JAR" "$DEPLOYMENT" -m scan
java -jar "$JBS_JAR" query "$WORKSPACE" scan-status --json
```

`WORKSPACE` 是部署包旁的 `.jbytescanner`。普通扫描及准备时间属于**工具接入成本**，不可在总成本比较中忽略；它可以按本轮任务数摊销，并与单个任务审计耗时分别报告。

### 任务清单模板

每条任务独立。审计 agent 只收到 `tasks.jsonl` 中的 `task_id`、`category`、`scope`、`question`、`time_limit_minutes`；裁决者在私有文件中用 `task_id` 关联真值。

```json
{
  "task_id": "srm-groovy-01",
  "category": "Groovy 脚本注入",
  "scope": "汉得 SRM 部署包中的 HTTP 入口及其调用代码",
  "question": "找出可由外部输入影响的 Groovy 脚本执行路径，并判断必要的利用条件；也可以报告证据不足。",
  "time_limit_minutes": 30
}
```

首轮不要把已知的 `POST /v1/rule-engine/run-script`、`GroovyShell.parse(String)` 或现有 finding 位置写进审计 agent 的任务文本，否则测到的是核对给定线索的能力，而不是发现能力。另设“给定 source/sink 的漏报诊断”任务时，可以提供精确签名，但必须同时提供给两组。

## 配对运行

每个任务均跑 A、B 两组；先固定主要评测模型为计划实际部署的本地模型。模型版本、量化方式、上下文长度、系统提示词、温度、工具超时、最大运行时间和最大 token/调用预算两组相同。更强模型可以再跑同样的 A/B，结果分层报告，不能跨模型直接归因于工具。

| 组别 | 额外工具 | 可见 JByteScanner 产物 |
| --- | --- | --- |
| A：搜索基线 | 无 | 否 |
| B：搜索 + CLI | `query`、`diagnose`、CLI `--help` | 仅通过 CLI 访问预扫描工作区 |

每个 `task_id × 组别 × 重复编号` 使用新会话，不继承记忆。至少做 2 次重复；任务多时可增加到 3 次。交错或随机安排 A/B 的运行顺序，避免机器负载和学习顺序偏差。审计 agent 只能在自己的预算内行动；超时按当时已提交的结果计分，不延长某一组。记录所有工具调用、stdout/stderr、退出码、墙钟时间、模型 token 用量及最终答案。输出过长时，模型可自行限制 `query --limit` 或用已有命令检查，但这些操作照常计时计费。

交给两组审计 agent 的共同指令：

> 你负责审计给定 Java 部署包的指定漏洞类别。使用可访问的代码和工具，在时间预算内找出具体、可复核的 source-to-sink 候选，并检查参数类型、转换、校验、净化、分支条件和调用上下文。工具报告只是线索；不要把端点级污点流当成完整利用路径，也不要把未命中当成安全证明。每条结论须指出证据与不确定性；若无法确认，明确返回 `uncertain`。只提交下述 JSON，不参考其他任务或运行的结果。

给 B 组追加这一段，A 组不追加：

> 你还可以使用 JByteScanner CLI：`java -jar "$JBS_JAR" query "$WORKSPACE" [findings|finding|scan-status] ... --json` 和 `java -jar "$JBS_JAR" diagnose "$DEPLOYMENT" --sink '<完整 Tai-e 签名>' ... --json`。先阅读必要的 `--help`。`query` 只按完整签名过滤；你需要自行定位签名。`diagnose` 会重新运行定向分析，时间计入你的预算。不要直接读取 `.jbytescanner` 下的 sidecar、SARIF 或诊断文件。

### 审计 agent 输出格式

每次运行提交一个 JSON 文件。可报告多条候选；没有候选时 `findings` 为空，但必须给出实际检查范围和限制。`verdict` 是 agent 自己的判断，裁决者会重新核实。

```json
{
  "task_id": "srm-groovy-01",
  "findings": [
    {
      "entry": "HTTP 方法/路径及入口方法；未知则写 null",
      "source": "可控输入、参数位置与类型",
      "sink": "危险调用及敏感参数",
      "verdict": "likely_exploitable | likely_not_exploitable | uncertain",
      "reason": "输入如何到达 sink，关键约束是什么",
      "evidence": ["可复核的类/方法/文件位置或命令证据"],
      "missing_evidence": ["尚未确认的条件"]
    }
  ],
  "checked_scope": ["实际检查过的包、入口或调用"],
  "limitations": ["时间、反编译缺失或证据边界"]
}
```

## 裁决与指标

裁决者先去掉组别标识，对两组发现按“同一入口、同一可控输入、同一 sink、同一根因”去重。依据代码或可控的隔离验证确认输入类型、数据传递、过滤、分支和 sink 语义。`likely_exploitable` 需要足够的可利用性证据；仅有端点污点流最多证明候选，不自动算正确漏洞。对运行环境、鉴权或动态条件无法确认的记录为 `uncertain`，不强行计入真/假阳性。无命中不能直接计为真阴性，除非该任务的真值范围已经独立建立。

逐任务记录：已核实正确问题数、错误结论数、遗漏的已知问题数、`uncertain` 数、从开始到首个正确问题的时间、总墙钟时间、模型 token/调用次数、`query`/`diagnose` 次数，以及 CLI 扫描准备时间。公开有完整标签的样本可计算 precision、recall、F1；真实部署包若真值不完整，报告“已核实正确问题 / agent 小时”和对已知问题的命中率，不宣称全量 recall。展示逐任务 A/B 差值及重复运行的波动，不只给总平均。

定义实验是否有实际收益时，预先确定主要指标（建议：固定 30 分钟内的已核实正确问题数），同时检查误报没有明显增加。若 B 组只因预扫描看到了大量候选而更快，也属于工具收益，但应连同预扫描耗时和内存单独报告；若收益只在给定精确 sink 签名时出现，应如实说明 CLI 的发现入口仍弱。

## 交付物与有效性检查

建议在测试电脑创建独立的 `experiment/` 目录，保存 `manifest.json`（版本、模型、预算、随机顺序）、`tasks.jsonl`、只供裁决者读取的真值文件、每次运行的提示词/工具日志/最终 JSON、裁决表和汇总表。不要把客户部署包、反编译代码、扫描报告或真实漏洞细节提交到公开仓库。

运行前检查：两组代码视图一致；A 组无法访问扫描产物；B 组 `scan-status` 的 Worker 为 `SUCCESS`；任务文本没有透露答案；预扫描与任务使用相同的部署包。运行后检查：会话隔离、预算相同、输出格式可解析、超时与失败已记录。任何一项不满足，应标记该次运行无效并在修复环境后整对重跑，不只补跑一组。
